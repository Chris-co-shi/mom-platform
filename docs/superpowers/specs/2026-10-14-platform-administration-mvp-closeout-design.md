# Platform Administration MVP 三大基础模块闭环设计

- 状态：待审核
- 日期：2026-10-14
- 范围：`mom-platform`、`mom-web`
- 目标模块：Auth、System、MDM

## 1. 目标与关闭口径

本轮目标不是完成整个 MOM 业务 MVP，而是关闭可独立交付的 **Platform Administration MVP**：管理员能够通过统一入口完成登录、身份与权限管理、系统基础配置以及主数据维护，并且关键成功路径、权限边界和失败路径具备可重复验证的证据。

三个模块只有同时满足以下条件，才标记为“基础模块已关闭”：

1. 前端页面、后端 API、数据库和运行时依赖形成真实可执行链路，而非仅有单层 CRUD。
2. 已有能力不重复开发；仅补齐当前缺失的管理入口、契约偏差和测试证据。
3. Gateway、业务 Resource Server、Redis Opaque Token、PostgreSQL 的认证与数据边界保持现状，不引入新的认证协议或基础设施。
4. Auth、System、MDM 各自达到本设计定义的验收标准，并通过跨模块端到端验收。
5. 未纳入的 MOM 业务域保持暂停，基础模块关闭后先进入业务建模讨论，再决定下一个业务 Slice。

因此，“三大基础模块关闭”代表平台管理底座可用，不代表 MOM 产品整体 MVP 已完成。

## 2. 当前实现判断

### 2.1 已完成，可直接复用

#### Auth

- Redis Opaque Token 登录、登出、当前用户查询链路已存在。
- 用户、角色、权限和资源管理后端能力已存在。
- 用户—角色、角色—权限关系接口已存在。
- Gateway 负责入口转发，各 Resource Server 继续独立校验身份和权限。
- `mom-web` 已有登录、用户、角色、权限和资源管理页面，角色—权限配置已有前端入口。

#### System

- 受限字典、支持语言和动态国际化是 System V1 的既定边界。
- System 负责注册表和管理面；动态国际化运行时能力位于公共框架并由所属服务承载。
- 后端已有字典、Locale、I18n 管理及运行时 bundle/change-stream 能力。
- `mom-web` 已有相应管理页面和请求封装。

#### MDM

- 已实现组织与制造静态结构：工厂、车间、产线、工位。
- 已实现仓储静态结构：仓库、库区、库位、库位类型。
- 已实现物料、物料分类、计量维度、单位类别、计量单位和单位换算规则。
- 后端已有对应 API、持久化和部分测试，`mom-web` 已有对应管理页面。

### 2.2 部分完成，必须在关闭前补齐

#### Auth

- 后端存在用户—角色读取与设置接口，但前端缺少对应管理入口，导致 IAM 管理链条不完整。
- Token 过期、用户禁用、登出失效、Redis 故障时拒绝访问等关键失败行为需要形成可重复验收证据。

#### System

- 字典状态修改契约存在路径偏差：前端使用 `/system/admin/dictionaries/{id}/status`，当前后端/OpenAPI 暴露为 `/{id}/status`。
- System 页面与 API 层缺少足够的前端自动化测试。
- Locale 切换、动态 bundle 和变更通知的组合链路需要形成验收证据。

#### MDM

- 当前能力广度已足以支撑平台管理 MVP，但需要冻结 MDM 与后续 WMS/MES 的所有权边界，避免后续重复建模。
- 需要用代表性前端测试和后端约束测试证明层级关系、状态限制、版本并发和单位精度行为。

### 2.3 本轮不实现

- OAuth 2.0、OIDC、JWT/JWK、Refresh Token、Client Credentials、外部身份提供商。
- System Parameter、Preference、Catalog、Navigation 等新的 System 子域。
- Supplier、Customer、BOM、Recipe、Routing、Workflow 等新的 MDM 或业务能力。
- MES、WMS、QMS、Traceability、EAM、EMS 业务功能。
- CQRS、Event Sourcing、Saga、Outbox、通用状态机、消息总线或新微服务。
- 新的生产依赖、大规模分层重构或为了目录一致而生成空模型。

## 3. 冻结的模块边界

### 3.1 Auth 边界

Auth 继续遵循当前 ADR-040：V1 使用 Redis Opaque Token。Gateway 不是唯一安全边界，System、MDM 等 Resource Server 必须继续验证身份与权限。

Auth 本轮负责：

- 用户、角色、权限、资源及其管理关系。
- 登录、登出、当前会话身份和 Token 生命周期。
- 向前端提供稳定的权限码，用于菜单与操作级可见性控制。

Auth 本轮不负责：

- 工厂/组织业务范围授权。
- 外部 IAM 联邦、第三方登录和机器身份。
- 跨业务域的数据权限策略平台。

### 3.2 System 边界

System 继续遵循 ADR-043，只包含：

- 受限字典。
- 支持语言注册表。
- 动态国际化管理面与运行时发布链路。

System 不吸收用户偏好、认证授权、业务主数据或通用配置中心职责。动态国际化数据仍由实际业务拥有者写入其本地 Schema；System 不跨 Schema 直接修改其他服务数据。

### 3.3 MDM 与 WMS/MES 的所有权边界

本轮采用“稳定主数据归 MDM，运行时业务状态归业务域”的边界：

- MDM 拥有工厂、车间、产线、工位、仓库、库区、库位、库位类型的稳定身份、编码、名称、静态层级和基础启停状态。
- WMS 后续拥有库存、占用、容量约束、容器—库位关系和仓储作业生命周期。
- MES 后续拥有生产能力、生产日历、设备/工位运行时状态以及工单执行生命周期。
- WMS/MES 通过 MDM 的字符串 ID 引用这些主数据，不复制一套同名主档，也不跨 Schema 建外键或 JOIN。
- 本轮不迁移现有表、不创建 WMS/MES 运行时表；只通过新 ADR 明确该边界，并使后续业务讨论以此为输入。

该边界会在实施阶段通过新的 Accepted ADR 取代 ADR-025 中与当前实现不一致的相关所有权描述，不静默修改既有决策历史。

## 4. 收口阶段与实施顺序

### Milestone M0：Platform Administration MVP 关闭

#### Slice M0-S1：当前基线收口

目标：先确认工作区已有的 I18n、配置、迁移、OpenAPI 和测试改动构成一致基线，避免在未知基线上叠加功能。

后端任务：

- 审查当前未提交改动，只修复与三模块关闭直接相关的编译、契约或测试问题。
- 核对 System V17 Migration、I18n Host 安全配置和各服务配置是否与当前 ADR 一致。
- 核对 Auth、System、MDM OpenAPI 快照与实际 Controller。
- 运行受影响模块验证；公共框架或契约影响扩大时升级为完整后端验证。

前端任务：

- 审查当前未提交的布局、Locale、System 页面样式和 HTTP Client 测试改动。
- 确认这些改动不会改变本轮冻结边界或掩盖既有失败。

依赖：无，是后续 Slice 的前置条件。

交付物：

- 可编译、可测试的当前基线。
- 已确认的 OpenAPI/运行时配置一致性。
- 已有脏改动的归属与验证记录。

验收标准：

- 相关后端测试与前端测试通过。
- 无未解释的契约漂移、Migration 冲突或安全配置降级。
- 不通过删除测试、放宽断言或关闭安全校验获得绿灯。

#### Slice M0-S2：Auth 闭环

目标：完成管理员从用户创建到权限生效的完整 IAM 链条，并验证 Token 失败语义。

后端任务：

- 复核并补强现有用户—角色接口、角色—权限接口和权限校验测试，不重复新增同义 API。
- 验证 Token 创建、读取、过期、登出删除和禁用用户拒绝访问。
- 验证 Redis 不可用或 Token 状态不确定时采用 Fail Closed。
- 验证 Gateway 转发后 Resource Server 仍执行自身身份与权限检查。

前端任务：

- 在现有用户管理中增加用户—角色读取和设置入口，复用既有角色选择及 IAM 页面模式。
- 使用既有 `GET /users/{id}/roles` 和 `PUT /users/{id}/roles` 契约。
- 按现有权限码控制查看与修改操作，不创造新的权限模型。
- 补充请求层、交互状态和关键页面测试，覆盖加载、保存、无权限、失败反馈和刷新后状态。

依赖：M0-S1。

交付物：

- 用户—角色前端管理闭环。
- Auth 核心成功与失败路径自动化证据。
- 真实登录—授权—登出验证记录。

验收标准：

1. 管理员可以创建/维护用户、角色、权限和资源。
2. 管理员可以为用户分配角色、为角色分配权限。
3. 新授权在重新获取会话权限后正确生效，越权操作返回 403。
4. 无效、过期、已登出 Token 返回 401；禁用用户不能继续访问受保护资源。
5. Redis 故障不会退化为匿名放行或绕过权限。

#### Slice M0-S3：System 闭环

目标：修正已知契约错误，并证明字典、Locale 和动态国际化链路可用。

后端任务：

- 将字典状态修改接口统一到 `/admin/dictionaries/{id}/status`，同步 OpenAPI 契约和测试。
- 补强受限字典、Locale 注册表、I18n 管理、运行时 bundle 与变更通知测试。
- 验证业务服务只操作自身 I18n 数据，System 不跨 Schema 写入。

前端任务：

- 保持现有 System 页面信息架构，不新增 System 子域。
- 增加 API 与关键页面测试，覆盖查询、创建/编辑、启停、删除限制和错误反馈。
- 验证 Locale 切换后 bundle 重新加载；变更通知可触发刷新，通知暂时中断时仍可通过下次加载恢复。

依赖：M0-S1；Auth 权限链路可用于完整验收，但 System 内部开发不必等待 M0-S2 全部完成。

交付物：

- 前后端一致的字典状态修改契约。
- System V1 三项能力的自动化测试和运行记录。
- 动态国际化管理面到运行时的验收证据。

验收标准：

1. 字典、Locale 和 I18n 的已有 CRUD/状态操作前后端一致。
2. 不允许的字典值、重复 Locale 或非法 I18n 写入得到确定的 4xx 结果。
3. 运行时按 Locale 返回正确 bundle，变更通知后客户端可获取新内容。
4. 无对应权限的用户不能访问管理接口。

#### Slice M0-S4：MDM 闭环

目标：在不扩展主数据范围的前提下，关闭当前已有 MDM 能力并固定其演进边界。

后端任务：

- 新增并接受 MDM 静态结构与 WMS/MES 运行时所有权 ADR，明确取代 ADR-025 的冲突部分。
- 核对现有组织层级、仓储静态层级、物料分类、物料和 UOM 模型的 API、权限、事务与数据归属。
- 补强代表性测试：父子层级完整性、重复编码、不存在引用、启停/删除限制、乐观锁冲突、换算精度与非法换算。
- 不新增供应商、客户、BOM、配方、工艺路线或库存字段。

前端任务：

- 为组织结构、仓储静态结构、物料和 UOM 各选择至少一个关键页面补充代表性测试。
- 覆盖层级加载、表单校验、关联选择、保存冲突、权限隐藏/拒绝和错误反馈。
- 核对前端 ID 全程按字符串处理，精度敏感数量不经过 JavaScript Number 的有损转换。

依赖：M0-S1；最终权限验收依赖 M0-S2。

交付物：

- MDM 所有权 ADR。
- 当前 MDM API/页面与数据约束的验收证据。
- 可供后续 WMS/MES 业务讨论直接引用的边界说明。

验收标准：

1. 工厂—车间—产线—工位、仓库—库区—库位以及物料/UOM 的现有管理链条可执行。
2. 重复编码、非法父子关系、不存在引用、版本冲突和非法换算得到明确失败结果。
3. 权限隔离有效，Snowflake ID 始终以字符串跨 JSON 边界传输。
4. MDM 表只落在 MDM 自有 Schema，不与未来 WMS/MES Schema 建跨域外键或 JOIN。

#### Slice M0-S5：跨模块最终验收与关闭

目标：用管理员真实路径证明三个模块可以作为独立的平台管理 MVP 关闭。

验收主链：

1. 管理员通过 Gateway 登录。
2. 创建用户、角色和权限关系，并为用户分配角色。
3. 新用户登录后只看到并只能调用获授权的 System/MDM 功能。
4. 维护字典、Locale 和动态国际化内容，运行时读取新内容。
5. 维护 MDM 组织、仓储静态结构、物料和 UOM 数据。
6. 验证 401、403、409、非法输入、Token 失效、版本冲突和依赖不可用等失败路径。
7. 执行后端与前端最终质量门禁，并记录真实 Redis/PostgreSQL/Gateway 条件下的验证范围。

依赖：M0-S2、M0-S3、M0-S4 全部完成。

交付物：

- 三模块关闭清单与验证证据。
- 更新后的权威 ADR、OpenAPI 快照和必要模块文档。
- 已知限制和下一阶段业务讨论输入。

验收标准：

- 全部主链步骤可重复执行。
- 自动化测试与真实链路验证结果均有记录，未运行项不得标记为通过。
- Auth、System、MDM 无阻断平台管理 MVP 的 A 类问题。
- 未完成项只允许是已明确排除的后续业务能力或可接受的非阻断风险。

## 5. 关键失败语义

- 未携带、无效、过期或已登出的 Token：401。
- 身份有效但缺少操作权限：403。
- 唯一键、版本或状态冲突：使用项目既有冲突响应语义，不通过覆盖更新规避。
- Redis 无法确认 Token 状态：拒绝访问，不降级放行。
- PostgreSQL 写入失败：由 Application 本地事务回滚，不留下半完成关系。
- 前端保存失败：保留用户输入并展示可操作的错误信息，不伪造成功状态。
- 动态国际化通知中断：不影响持久化正确性；客户端可通过重新拉取 bundle 恢复。
- 外部 HTTP 写请求：不新增自动重试，避免重复写。

## 6. 测试与验证策略

### 6.1 后端

- 每个 Slice 先执行受影响模块的单元/集成测试。
- 统一使用仓库脚本，例如 `bash scripts/codex-verify-changed.sh` 和 `bash scripts/codex-mvn-test.sh`，先读取有界诊断摘要。
- Auth 安全、公共 I18n、OpenAPI、Schema 或共享契约变更触发扩大验证。
- 最终收口执行后端完整质量门禁，并明确哪些验证使用真实 Redis、PostgreSQL 和 Gateway，哪些仍是测试替身。

### 6.2 前端

- 优先执行新增测试所在模块的 Vitest 用例。
- 每个 Slice 完成后执行类型检查、Lint 和受影响测试。
- 最终执行 `pnpm verify` 或仓库等价完整门禁。
- 页面测试关注业务交互和失败反馈，不为 getter、静态文案或实现细节堆砌低价值断言。

### 6.3 契约与端到端

- Controller、OpenAPI 快照和前端 API 路径必须一致。
- 端到端验收至少覆盖 Gateway → Resource Server → Application → PostgreSQL/Redis 的真实调用链。
- 真实中间件未运行时只能声明编译或替身测试通过，不得推断生产兼容性。

## 7. 交付后的当前状态

M0-S5 通过后：

- Auth：关闭为 Platform Administration MVP 的身份与权限模块。
- System：关闭为受限字典、Locale 和动态国际化模块。
- MDM：关闭为当前静态主数据模块，并以 ADR 固定与 WMS/MES 的边界。
- MOM 整体：仍处于业务模块启动前，不标记为完整 MVP。

下一阶段不直接编码。先围绕真实业务流程讨论第一个业务 Slice，至少明确参与角色、触发事件、核心对象、状态流转、失败与补偿、数据所有权以及与 MDM 的引用关系，再选择 MES、WMS、QMS 或其他域的实施顺序。

## 8. 审核即确认的决策

批准本设计意味着确认以下决定：

1. 先关闭 Auth、System、MDM，再进入 MOM 业务域讨论。
2. 三模块组成的是 Platform Administration MVP，而不是完整 MOM MVP。
3. Auth V1 保持 Redis Opaque Token，不在本轮升级为 OAuth/OIDC/JWT。
4. System V1 保持受限字典、Locale、动态国际化三项能力，不扩展通用配置域。
5. MDM 拥有制造与仓储对象的稳定静态主数据；WMS/MES 后续拥有各自运行时状态和业务生命周期。
6. 实施顺序为 M0-S1 → M0-S2/M0-S3/M0-S4 → M0-S5；其中最终验收必须等待三个模块分别收口。
7. 本设计审核通过后，下一步先生成逐任务实施计划供审核，不直接跳过计划进入编码。
