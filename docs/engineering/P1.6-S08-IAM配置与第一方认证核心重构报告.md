## 2. 重构前职责图

```text
IamAuthorizationServerConfiguration
├─ 账号 AuthenticationProvider / Client Policy / Authorization Context
├─ Session / Refresh / revoked sid Bean
├─ SAS JDBC Store / Public Client
├─ JWK / Encoder / Decoder / Token Generator / inline Claims
├─ SAS FilterChain
├─ HTML Login + API FilterChain
└─ 页面 Controller / /api/iam/me Router

IamDirectAuthenticationController
├─ HTTP DTO 与校验
├─ 凭据认证与 Client Policy
├─ 审计上下文与首次改密编排
├─ Session 初始签发
├─ JWT 签发
├─ Refresh Rotation
└─ Logout 撤销
```

主要问题不是协议能力重复，而是配置装配与第一方 Web Adapter 同时承担过多职责；
`IamSessionJwtIssuer` 与 SAS inline Customizer 还各自维护一段核心授权 Claims 组装逻辑。

`IamSessionTokenService.rotate`；JSON Logout 与管理员撤销继续调用同一 Session 撤销能力。

## 4. 配置类拆分

| 配置 | 保留职责 | 行为保持点 |
|---|---|---|
| `IamAuthorizationServerConfiguration` | AutoConfiguration 条件、属性注册、配置导入 | 条件、Profile、启用开关不变 |
| `IamAuthenticationCoreConfiguration` | 账号认证、Client Policy、Context Loader、Session、第一方用例装配 | 原 Bean 名称保留；AuthenticationProvider 仍为 Primary |
| `IamTokenInfrastructureConfiguration` | Settings、JWK、Encoder/Decoder、Claims、Token Generator、Issuer | 唯一 JWKSource；RS256、`kid`、Issuer 不变 |
| `IamAuthorizationServerProtocolConfiguration` | 官方 JDBC Store、Public Client、SAS Chain、标准 Refresh Adapter | `@Order(HIGHEST_PRECEDENCE)`、Matcher、PKCE/OIDC 与标准错误不变 |
| `IamLoginPageSecurityConfiguration` | HTML Login、Cookie Session、普通 Bearer API、`/api/iam/me` | `@Order(2)`、CSRF/Form Login/Logout/Session Fixation 不变 |
| `IamDirectAuthenticationConfiguration` | 第一方 JSON Chain | 未拆分；`@Order(1)`、Matcher 与 Stateless/CSRF 现状不变 |

没有引入 `@Lazy`、新增 `@Primary`、循环依赖或新生产依赖。SAS 官方 JDBC Store 的 ArchUnit 精确
例外从旧聚合配置类迁移到唯一的 `IamAuthorizationServerProtocolConfiguration`，没有扩大排除范围。

## 5. 第一方登录 Application Service

`IamFirstPartyLoginApplicationService` 接收协议无关的内部 Command 与服务端请求元数据，保持原顺序：

1. 使用现有 `AuthenticationProvider` 校验用户名和密码；
2. 使用现有 `IamClientAccessPolicyService` 校验可信 Client Policy；
3. 以 `accounts.requireUser` 建立原有审计 Actor；
4. 登录成功先记录成功审计，再判断首次改密；
5. 首次改密先修改密码、再记录成功、再创建 Session；
6. 调用唯一 `IamSessionTokenService.issueInitial`；
7. 调用唯一 `IamAccessTokenIssuer`；
8. 返回不依赖 Servlet、Controller DTO 或 OAuth2 HTTP Request 的内部结果。

Controller 只保留 Request DTO、已有空值校验、设备名规范化、Servlet 元数据提取、Command/Response
转换和 Refresh/Logout 的薄 Adapter。账号锁定、禁用与凭据错误继续收敛为同一泛化错误，未扩大枚举信息。

## 6. 授权上下文、Claims 与 Token 签发

### 6.1 `IamAuthorizationContextLoader`

由原 `IamAuthorizationContextService` 按真实职责更名，复用原 Repository 查询和账号/Party 状态校验；
不接受客户端 Claims，不签 Token，不创建 Session。为内部 Bean Name 兼容保留
`iamAuthorizationContextService` 别名。

### 6.2 `IamJwtClaimsAssembler`

无状态、无数据库和无 HTTP 依赖。统一组装 `sub`、`client_id`、`user_type`、`sid`、Role、Permission、
Factory、Party，以及 ID Token 当前已有的 `preferred_username`/`name`。核心安全 Claim 使用精确 allowlist
进行双通道等价比较；协议动态或专属字段不被大型 Snapshot 隐藏。

### 6.3 `IamAccessTokenIssuer`

取代 `IamSessionJwtIssuer` 的职责名称，但继续复用同一 `JwtEncoder`、JWK、RS256、`kid`、Issuer、
Audience、调用方提供的 TTL 和统一 Claims Assembler。它不构造伪 OAuth2 Grant Context，不加载数据库，
不创建 Session/Refresh。标准 Refresh Adapter 只把内部签发结果映射回 SAS 的 `OAuth2AccessToken`。

### 6.4 SAS 组件复用裁决

标准 Authorization Code/OIDC 继续使用 SAS `JwtGenerator`/`OAuth2TokenGenerator`；第一方 JSON 不强行
复用需要 `JwtEncodingContext` 的协议组件，因为这会要求伪造 Grant、Registered Client 或 HTTP Request
上下文。第一方签发器选择协议中立的 `JwtEncoder` 包装，避免复制密钥加载和签名代码。

## 7. 等价证据

### 7.1 FilterChain

| Chain | Order | Matcher/主要语义 | 结果 |
|---|---:|---|---|
| SAS/OIDC | HIGHEST | SAS Endpoints Matcher、HTML Entry Point、PKCE/Client Policy Filter | 保持 |
| 第一方 JSON | 1 | `/api/iam/auth/**`、Stateless、登录/改密/Refresh 公开、Logout Bearer | 保持 |
| HTML/API | 2 | Form Login、默认 CSRF、Cookie Session、`/api/iam/me` Bearer | 保持 |

### 7.2 第一方 JSON

特征测试锁定登录成功、泛化凭据错误、账号不可用、Client Policy、首次改密、Refresh、Logout、
`/api/iam/me`，以及 Method、Path、Content-Type、字段名称/类型、状态码、错误码、no-store 和签发/撤销调用。

### 7.3 OAuth2/OIDC

Public Client 测试锁定 `ClientAuthenticationMethod.NONE`、Authorization Code、Refresh、PKCE、Refresh
不复用、10 分钟 Access Token 与 RS256 ID Token；显式断言不存在 `grant_type=password`。标准 Token
响应继续使用 `access_token`、`token_type`、`expires_in`、`scope`、`refresh_token`，未被第一方 JSON 包装。

JWK、Discovery、Authorization Endpoint 与 OIDC Endpoint 仍由同一 SAS 配置启用；S08 未修改 endpoint
settings、matcher 或 handler。完整跨仓库协议 E2E 仍归 S10。

### 7.4 Claim 等价矩阵

| Claim | PC JSON | Authorization Code/OIDC | 规则 |
|---|---|---|---|
| `sub`、`sid`、`client_id`、`user_type` | 有 | 有 | 必须等价 |
| `roles`、`permissions`、`factory_ids` | 有 | 有 | 名称、集合类型和值必须等价 |
| `party_type`、`party_id` | 外部用户有 | 外部用户有 | 缺失与存在规则必须等价 |
| `iss`、`aud` | 有 | 有 | 同一 Settings/Client 语义 |
| `iat`、`exp`、`jti`、`auth_time` | 动态 | 动态 | 按类型、期限与协议规则比较 |
| OIDC `nonce`、ID Token 展示 Claim | 无 | 协议需要时有 | 精确允许的协议专属字段 |
| 第一方外层 `refreshToken`、`sessionId` | JSON 响应 | 不进入标准 Token 响应 | Adapter 专属，不进入 JWT 核心 |

### 7.5 Session / Refresh / Reuse Detection

新增测试冻结八小时 Web 绝对 Session、十分钟 Access、sequence=1 初始 Refresh、Rotation 的旧状态消费与
唯一后继顺序、重放后的 COMPROMISED + revoked sid、到期 EXPIRED + fail closed、显式撤销的数据库后
revoked store 顺序。生产事务注解、`FOR UPDATE` Repository、`noRollbackFor` 与所有 Redis 行为均未改动。

## 8. 事务、锁与审计

- `@Transactional` 仍只位于原 `IamSessionTokenService` 公共方法；
- Application Service 不新增或移动事务；
- Session/Refresh 行锁、持久化顺序、单 ACTIVE 与唯一约束不变；
- 失败后的 EXPIRED/COMPROMISED 安全事实提交语义不变；
- 第一方登录和首次改密的 AuditActor 建立位置与动作顺序不变；
- Token 仍在权威 Session 创建或 Rotation 成功后签发，签名失败不伪造成功。

## 9. EG-02

状态：**Open**。

当前仓库只提供“外部流量经 Ingress → Gateway → 内部服务”的架构约定；业务服务仍配置独立监听端口，
本仓库没有可验证的 Kubernetes NetworkPolicy、Service exposure 或 `mom-infra` 固定版本证据证明其绝对
不可直连。因此 S08 不宣称部署隔离已经闭环，也不修改 Gateway/Resource Server/Redis。

S10 关闭条件：固定部署清单版本，验证 Service 类型与 NetworkPolicy；或为所有可直连业务 Resource
Server 提供 revoked sid 等价能力，并覆盖 Gateway 绕过、Redis 故障、Session 撤销和恢复回归。
