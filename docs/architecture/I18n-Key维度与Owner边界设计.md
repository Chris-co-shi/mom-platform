# I18n Key 维度与 Owner 边界设计

**状态：已确认，2026-10-14**  
**适用范围：Auth、MDM、System 服务自有 I18n 数据与 mom-web 管理/运行时调用**

## 1. 目标与边界

I18n 不再使用 namespace。每个服务仍拥有自己的 I18n 数据和数据库 Schema；Owner 是服务边界（Auth、MDM、System），不是 Key 的组成维度。不同 Owner 可以存在相同 Key，同一 Owner 内 Key 全局唯一。

本设计不合并服务数据，不改变 Locale、占位符、错误码、事务与服务间数据所有权。移动端当前没有动态 I18n 调用，本次不改其运行时。

## 2. Key 规则

- Key 是文案定义的唯一身份；保存后不可改名，同一 Owner 内不得重复。
- 写入前统一转换为小写（服务端使用 Locale.ROOT）；前端提交规范化后的小写值。
- Key 不得包含空格、空白符、全角字符或其他非 ASCII 字符。输入不做 trim 或全角转换，提示用户修正。
- 合法格式：`^[a-z][a-z0-9]*(?:[._-][a-z0-9]+)*$`，长度 1～160。
- 大小写不同的输入会规范化为同一 Key；碰撞时拒绝写入并提醒用户，不自动覆盖、合并或改写既有定义。
- 不同 Locale 的同一文案必须复用同一 Key。精确相同的译文文本可以出现，但保存前提示同 Owner、同 Locale 下已使用该文本的 Key；用户确认后仍可保存。此规则是提醒，不是数据库唯一约束。

## 3. 存储与运行时

每个 Owner 继续使用本 Schema 的消息定义和译文表。消息定义表删除 namespace 列，以 `message_key` 建立跨启停/逻辑删除状态的唯一约束；译文仍以消息 ID 和 Locale 唯一。运行时一次读取当前 Owner 下启用的消息，返回扁平 `messageKey -> text` 映射。Locale 回退和占位符校验保持不变。

修改任意定义或译文后，SSE 失效通知只需表达 Locale（或全部 Locale）；服务自身就是 Owner 边界，不再按 namespace 分组或筛选。

## 4. 迁移策略

新增 Flyway Versioned Migration，不修改历史脚本。迁移先检查实际数据在小写化后是否冲突；冲突时以明确错误中止，不合并记录。根 Owner namespace 下仅用于组成错误码的局部 Key，会转换为完整稳定 Key（例如 `error.x` 转成 `auth.error.x`）；其他已有 Key 原样小写化。随后移除 namespace 约束与列，建立 Owner 内唯一 Key 约束和小写格式约束。

上线前必须检查迁移冲突诊断。生产数据存在冲突时由业务人员确认各记录的归并/改名方案后再执行迁移，不由脚本猜测。

## 5. 重复译文提醒接口

管理端在保存译文前可查询同 Owner、同 Locale、精确文本相同且属于其他 Key 的定义。此查询只用于提醒，不占用或锁定文本；并发下提醒结果可能变化，最终是否允许保存不受此查询结果影响。
