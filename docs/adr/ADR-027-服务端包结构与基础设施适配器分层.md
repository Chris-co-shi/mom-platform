# ADR-027：服务端包结构与基础设施适配器分层

- Status：Accepted
- Date：2026-07-30
- Decision Owner：Chris
- Scope：正式 bounded context 的 `mom-*-server/src/main/java`

## Context

MOM 已冻结 Web、Application、Domain 与 Infrastructure 的依赖方向，但部分 Server 仍在
`infrastructure.persistence` 下按 Parameter、Dictionary、I18n、Admin 等业务 Feature 建立小型技术烟囱。
这种目录同时混合业务能力与技术职责，使 Entity、Mapper、Repository 和查询投影的位置不稳定，也增加
Mapper XML Namespace、组件扫描、反射字符串和 ArchUnit 规则在重构时遗漏的风险。

Chris 已明确选择混合组织方式：靠近业务的层按业务能力分包，外部适配层按 Adapter 技术类型分包。本 ADR
对该选择收口，不再把是否采用该结构作为开放问题。

## Decision

1. Domain、Application、Web 按业务能力或用例组织，例如 `domain.dictionary`、`application.i18n`、
   `web.parameter`；禁止退化为全局 `domain.entity`、`application.service` 或 `web.controller`。
2. Infrastructure 以 Adapter 类型为第一组织维度，只允许实际需要的 `persistence`、`client`、`messaging`、
   `cache`、`storage`。Spring 装配位于 bounded context 顶层 `configuration`。
3. Infrastructure Persistence 以技术职责为第一组织维度：`entity`、`mapper`、`repository`、`query`、
   `converter`、`typehandler`。禁止 `persistence.parameter`、`persistence.dictionary`、
   `persistence.i18n`、`persistence.user`、`persistence.role`、`persistence.admin` 等 Feature-first 包。
4. 普通 Entity、Mapper、Domain Repository Adapter 和专用查询模型分别进入上述职责包。扁平包出现重名时，
   使用 bounded context 内完整业务前缀解决，不以 Feature 子目录规避。
5. Mapper XML 保持现有资源根，文件名、Namespace 和 Java Mapper 一致；移动 Java 类型必须同步更新所有
   Fully Qualified Class Name、`resultType`、`typeHandler`、扫描配置、测试和文档引用。
6. 不创建空目录、占位类型或无职责 `package-info.java`；不因目录重构增加通用 CRUD、Converter 或兼容代理。

## Alternatives

| 方案 | 结论 | 权衡 |
|---|---|---|
| 所有层都按业务 Feature 垂直切分 | 拒绝 | Infrastructure 内重复形成 Entity/Mapper/Repository 小烟囱，技术治理难统一 |
| 所有层都按技术类型水平切分 | 拒绝 | Domain/Application/Web 丢失业务语义，用例变更跨越大量全局技术包 |
| 混合组织：业务层 Feature-first、基础设施 Adapter-first | 接受 | 业务语义与适配器职责同时清晰，代价是需要明确边界门禁 |
| 保持现状，只靠 Review | 拒绝 | Package、路径和 XML 字符串错误无法稳定阻断 |

## Consequences

正面结果是持久化类型位置可预测、依赖方向可自动验证、同类 Adapter 集中治理，跨 Feature 的 Repository
转换仍保持局部私有。代价是首次迁移会产生较多纯移动和 import/Namespace 差异；扁平职责包要求类型名称在
bounded context 内唯一。迁移必须拆分提交并以模块测试、PostgreSQL IT 和 packaged smoke 证明行为不变。

## Scope

强制范围为 `mom-*-platform/mom-*-server/src/main/java` 中的正式 bounded context Server，包括实际存在代码的
System、IAM、MDM、Integration、MES、WMS、QMS、EMS、EAM 和 Traceability。`*-api`、`*-client`、Framework、
Gateway 和 Architecture Tests 不直接套用目录模板，但必须审计是否承载了应归属 Server 的正式业务持久化代码。

## Exceptions

Spring Authorization Server 官方协议配置、Framework AutoConfiguration、Framework Outbox/Inbox、通用
PostgreSQL TypeHandler 和 Phase 01 技术 Probe 可按其架构角色保留不同结构。例外必须精确到文件或类型，说明
理由与退出条件；禁止模块、目录或通配符白名单，且不得作为新业务实现模板。

## Migration Strategy

1. 先建立规范、模板、静态门禁与 ArchUnit 适应度函数，并精确登记待迁移类型。
2. 按 bounded context 使用 `git mv` 移动文件，同步 Package、import、XML Namespace、扫描配置、测试和文档。
3. 每个主要模块先 `test-compile`，再运行 `test/verify`；不得通过扩大可见性或复制旧类绕过编译错误。
4. 删除全部迁移期精确例外和空旧目录，扫描重复 FQCN、旧 Package 字符串与孤立 XML。
5. 运行 PostgreSQL IT、packaged smoke、全 Reactor 与最新 Head CI。

## Verification

- Package Layout Baseline 验证路径/Package、Entity/Mapper/Repository/Query 位置、Adapter-first 目录和 XML 引用。
- ArchUnit 验证 Persistence 各职责包的依赖方向、Web/Application/Domain 边界和类型位置。
- 编译与测试验证 Spring Bean、Mapper 注册、package-private 可见性和测试引用。
- PostgreSQL IT 与 packaged smoke 验证 Mapper/XML/Repository 移动不改变 SQL、Flyway、事务或 Readiness。
- Git 扫描验证无重复类、无旧目录、无遗留 FQCN，且所有移动保留历史。

## Rollback

每个模块移动使用独立普通 Commit。若验证失败，追加反向 `git mv` 和引用修复 Commit，不 reset、rebase、amend
或改写历史。Package 重构不包含数据库或协议变更，因此回滚只涉及源码路径与字符串引用；禁止保留双包兼容类。
